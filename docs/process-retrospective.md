# 流程复盘：spec → 计划 → 子 agent 实施 → 审查

2026-09-03，fa 项目 M1+M2 全程（20 个任务、3 轮终审修复波、~35 个审查席位）的流程沉淀。
目的：把「计划缺陷被链条拦截」的模式提炼出来，供以后任何项目的 writing-plans 环节自检。

## 数字概览

| | M1 | M2 |
|---|---|---|
| 任务数 | 10 | 10 |
| 计划缺陷（brief 自身有错，被实施者/审查者拦截） | 7 | 8 |
| 修复轮 | 2（每轮 ≤1 次） | 4（每轮 ≤1 次） |
| 重大拦截（若漏过将污染结论） | ingest 无回滚/空输入抹分区 | global_targets 衰减方向反（≈2353×） |

> 计数口径：计划缺陷按各里程碑报告的编号清单（m1-report 7 例、m2 台账 8 例）；审查另发现的计划级遗漏（如 M1 ingest 回滚缺失）未计入编号。
| 最终测试 | 45 | 90 |

约 **一半缺陷出在计划里的测试代码**，而非生产代码——「测试代码不用像生产代码一样严谨」是最贵的错觉。

## 九条自检清单（写计划时逐条过）

1. **时间炸弹**：测试放行条件不得依赖当前日期。实例：M1 Task 7（`fa data sync-history`）的 fake 下载器按 `start_year < 1995` 放行，写作时能过、今天必产 32 个文件使断言崩。修法：精确枚举 `(league, season)` 对。
2. **方向性代入**：每个带方向的量在计划期做一次符号小例。实例：`global_targets` 衰减写成 `0.5**((date−asof)/hl)`——date<asof 使指数为负、越老权重越大（1120 天窗内约 2353×，2^11.2），直接进判决路径。纸面代入 asof 昨天/一年前各算一次权重即可发现。
3. **阈值可达性先验算**：断言阈值与守卫/机制不矛盾。实例：弱数据测试 n=20 撞拟合的 `<30` 守卫；收缩幅度界 0.3 vs 实测 MAP 0.366（机制正常，阈值拍错）。修法：机制断言（相对比较）优于绝对阈值。
4. **mock/补丁顺序与目标**：先 patch 后取路径（先取真实路径会把夹具写进仓库再触网）；`from X import f` 的绑定免疫 `X.f` 模块级 patch——要么属性访问，要么 patch 消费方命名空间。
5. **命名契约逐一核对**：fixture 里的文件名/键名与生产构造函数对照。实例：夹具 `E0_1995.csv` vs 真实命名 `E0_9596.csv`（season_code(1995)="9596"）——逐字照抄会让验收门全红。
6. **单一事实源**：同一 DDL/公式/常量出现两处必单源化。实例：schema 迁移与 `_SCHEMA` 各持一份建表 DDL，`_SCHEMA` 先行使迁移成死代码、未来 schema 升级静默分叉。修法：模块级常量共享 + 形状一致测试。
7. **环境敏感性**：沙箱环境变量改变 CLI 输出形态（`FORCE_COLOR=3` 让 typer 的 rich 高亮拆断纯文本断言）。修法：conftest 以 setdefault 固定测试环境。
8. **禁用「先错后改」双版本段落**：计划里出现「上面这段删除、以下面为准」必然踩雷（实施者不知道该信哪段）。写完计划做一次占位符/双版本扫描再提交。
9. **诚实条款预写**：判决/统计类任务的验收步里预写「不得调参凑结论」「口径必须分开表述」。实例：M2 判决书把 edge 通过率(88.4%)与下注覆盖率(74.9%)混读——若 spec 期预写口径定义，修复轮就不用花在措辞上。

## 流程层的三个有效模式

- **实施者先跑再提交**：M2 Task 6 实施者在提交前实测种子数据，以 NEEDS_CONTEXT 拦截了不可满足断言（预检表自己判断错了「拟合仍收敛」）——带测量证据的升级请求比事后修复便宜一个数量级。派单时明确「测量优于推断」。
- **裁定分级**：控制器对 plan-mandated 发现必须当场裁定——载荷型（后续任务依赖，如衰减方向）立即修；孤立型（如 fit_rho 平坦似然端点）停放台账、终审统一清账。「项目止步则延后即永久」是例外：终审前把停放项全部清了。
- **判决完整性独立复现**：最高风险产出（go/no-go）由未参与实施的审查者用独立实现逐位复现（11,605 行、35/35 组、10 格校准全对上）——这一步排除了「harness 假象错杀项目」的可能，值得在任何判決类任务保留。

## 诚实的账

- 链条没有白跑，但**缺陷的源头几乎全在计划**：上表 15 例（M1 7 + M2 8）台账缺陷全部源自 brief 本身（实施者均逐字落地、被审查拦在提交前或修复轮）。但「台账之外实施者零失误」**不成立**——至少 3 例实施者自有错误被审查/终审抓回：M1 Task 10 修复提交误删唯一语义断言（808cacf 恢复）、M1 报告数字笔误（568e5d8 订正）、M2 终审修复波前 commit 置于 try 外与 audit 重复命名约定（8143fcd 收口）。writing-plans 的代码块应当享受与生产代码同级的推演强度——这是本复盘唯一真正的新知识，其余是纪律重申。
- 修复轮从未超过 1 次——缺陷都在纸面可发现层级，没有需要架构返工的。这说明缺陷类别可控、清单可防。
