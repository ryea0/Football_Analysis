## 1. 背景与动机

**过程事实先行**：项目负责人最初设想「用 hermes 自进化机制深化沉淀每个联赛经验」。该设想在 M2 NO-GO 后的严谨化转向中**未进 spec 即消失**——spec v0.4–v0.6 全文无进化/记忆/学习条款，连「被否决的备选」记录都没有。它不是输给论证，是被静默丢弃（教训：被放弃的意图也要留 ADR 痕迹）。本设计把它以可测量的形态接回。

现状是三条线路都不能自进化，且都是刻意的：

| 线路 | 进化方式 | 为什么不能自学 |
|---|---|---|
| 线 P（Python 管线） | 人改代码改 spec | 确定性主控（§2.2），数字必须可复现 |
| 线 A（dsh 当大脑，§12.5） | 无 | 每场独立无状态会话（可重放、可审计） |
| persona 层（hermes -z，M4） | 无 | 纯函数调用，串行逐场（M4 设计 B1） |

「不能自进化」的共同理由是同一组：可替换性（agent 不绑架架构）、测试路径（mock 与实跑同代码路径，有状态即分叉）、测量纯度（treatment 漂移则结论不可归因）。

## 2. 定位与结论分账

- **命名澄清**：C 线为第三条**顶层**线路（与 A 线研究评测、B 线 paper 运营并列）。勿与「线 A」（dsh 范式子线，属 A 线）混淆
- 性质：**元循环**——不与 A/B 线并行跑批，而是作用于 B 线消费的版本化工件（`personas/*.md` 与新增 `personas/knowledge/*.md`），产出物 = 版本
- C 线产出**永不直接进推荐流**：它只改变下一窗口 B 线 run 读到的工件内容
- C 线无 DB 写权：只读台账聚合；工件变更以 git diff 呈现，人审关卡裁定合并
- 结论分账沿用 §12 协议：C 线自身的有效性单独记账（§7），不与 B 线判据混排

## 3. 进化闭环形态

```
B 线窗口（treatment 冻结，§12.3，≈6 周/窗口）
  比赛日 × N ── 判决/落注/结算（每行记工件版本戳，D6）
        │ 窗口结束
        ▼
C 线进化事件（离线、独立调度、串行）
  ① 读台账聚合：本窗口 判决 vs 结果、双轨差（model_only/model_persona）、CLV
  ② hermes -z 反思纯函数（输入=知识库现状+窗口证据；输出=变更契约 JSON）
  ③ contract 校验 → apply 成 git diff
  ④ 诚实关卡：人审（台账数据辅助），全量记 Ruling
  ⑤ 合并 v_{n+1}；或拒绝/搁置（同样记 Ruling）
        │ 下一窗口开始
        ▼
B 线新窗口（判决 prompt 含知识库 v_{n+1}，版本戳随之更新）
```

## 4. 核心决策

| # | 决策 | 理由（含被否方案） |
|---|---|---|
| D1 | **状态外置为 git 版本化文件**，不用 hermes/dsh 内部记忆 | 三重冲突（可替换性/mock 路径/测量纯度）；被否：agent 内置记忆——测试与归因同时失效 |
| D2 | **窗口冻结制**：版本合并只发生在 B 线 §12.3 前向窗口之间 | B 线预注册判据要求 treatment 冻结，中途换版本即破协议；被否：协变量制（随时合并+版本作协变量）——每版本每联赛几十个判决，统计上永远悬而不决，还弱化 B 线判据 |
| D3 | **反思者仍是 hermes -z 纯函数**（与 M4 caller 同构） | 「谁思考」与「状态放哪」分离：LLM 负责反思与写作，记忆在文件。每窗口每联赛 1 次调用，成本可忽略 |
| D4 | **关卡 = 人审为主、台账数据辅助** | 样本量诚实条款：判决级反馈撑不起统计自动判；被否：统计自动合并门槛——纸面可达性不成立（writing-plans 清单第 3 条的同类错误） |
| D5 | **最简 v1**：markdown 知识文件直接内联进判决 prompt；无检索、无 embedding、无知识框架 | 最简形态被证明不够用之前，复杂机制即浪费；升级条件写进滚动报告而非预支建设 |
| D6 | **版本戳强制入账**：每条判决/注记录所用 personas 树版本 | 可归因的命根；机制（git rev vs 内容 hash）实施定，要求不变：任意一行可回答「当时知识库是什么」 |

## 5. 知识文件与反思契约

`personas/knowledge/{league_key}.md`，三段式：

1. **结构性认知**：不易过期的联赛特性（升班马风格、德比格局、裁判尺度、气候/旅途）——球探笔记性质
2. **时效段**：带日期，自动过期（参数实施定）
3. **教训段**：带日期 + 台账证据引用（哪几场、什么判决、结果如何）

反思输出契约（JSON，校验失败=本轮进化事件降级，知识文件不动）：

```json
{
  "league": "bundesliga",
  "appends": [{"section": "教训", "text": "...", "evidence": {"fixtures": ["..."], "stat": "veto 3 注全部误杀，均价损失 x%"}}],
  "amendments": [{"target": "旧条目锚点", "text": "...", "reason": "..."}],
  "deprecations": [{"target": "...", "reason": "..."}],
  "no_change_reason": "窗口证据不足时显式说明"
}
```

两条反偏差设计：

- **防事后诸葛**：每条 append 强制引台账证据；关卡人审抽查证据链
- **防回音室**：反思必须显式处理旧条目（amend/deprecate），滚动报告披露「本期被推翻/削弱的旧条目数」作为知识库健康度指标——只增不改的知识库是坏的

## 6. 接入契约与安全边界

- 独立 cron、离线串行；B/A 线 run 期间 C 线不存在
- 只读台账，只写版本化工件；无 DB 写权、无落注通道、无 Odds API 调用
- 失败即静默停摆：下一版本不来而已，记事件台账（runs 风格），不触碰任何线
- 版本拾取时机 = run 开始时快照；run 中途合并的版本对本 run 不可见

## 7. C 线判据预注册（草案）

**v1 不设统计合并门槛**——这是预注册的诚实内容本身（每版本每联赛几十个判决，统计分辨不可达）。合并由人审关卡裁定并全量记 Ruling 台账（事后可翻案，对齐负责人裁定授权惯例）。

滚动报告 `docs/evolution/report-YYYYMMDD.md`（descriptive，不设终止判据，同线 A 风格）：

- 知识库 persona 轨 vs 无知识库 persona 轨：轨道级 ROI 差、误杀率（被 veto/downweight 的注的实际收益）、CLV 对比
- 按版本分窗口呈现，版本戳串联（D6）
- 统计判据列为 ≥2 个窗口数据积累后的**后续注册项**，届时先改本节再启用——不得回溯套用

## 10. 非目标（明确排除）

- 不做统计调参/数字学习——数字归模型与 Python 主控（§2.2）
- 不做无人审自动合并
- 不给 hermes/dsh 常驻记忆、会话状态或常驻分析进程
- 不建检索/embedding/知识框架（D5 最简形态不够用之前）
- 不因 C 线改动 M5 节流优先级
- 不给 C 线任何 DB 写权、落注通道、真实下单通道（§7.2）
